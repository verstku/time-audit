## Процесс разработки

### Задачи и ветки
- Новая задача — это новая фича, исправление или служебная правка, которую я явно начинаю (в том числе запуск /prd-project, /prd-features, /prd-feature). Продолжение начатой задачи (планирование, обсуждение, выполнение плана, правки после ревью, /prd-spec и /prd-done в ветке этапа) — это НЕ новая задача, даже если это новая сессия.
- Когда я начинаю новую задачу, до brainstorming и любых изменений файлов предложи ветку: имя (feature/<кратко>, fix/<кратко>, chore/<кратко> или docs/<кратко>) и от какой ветки её создать (обычно main после git pull). docs/ — для /prd-project, /prd-features и описания уже сделанных фич. Если есть открытые PR (`gh pr list`) или незакоммиченные изменения — упомяни их. Создавай ветку только после моего ответа.
- На main файлы не меняй и не коммить. Если ты на main, а нужно изменить файлы, — спроси меня.
- Git worktrees не используем: работаем в этой папке на обычной ветке (ответ на вопрос using-git-worktrees — «нет», спрашивать не нужно).

### Superpowers
- Спеки и планы сохраняй в пути по умолчанию Superpowers (docs/superpowers/specs/ и docs/superpowers/plans/) и пиши их на русском.
- План выполняй через superpowers:executing-plans. Выбор способа выполнения в конце writing-plans не предлагай. Subagent-driven — только по моей просьбе.
- Визуальный помощник brainstorming (браузер) не предлагай.
- Финальное ревью ветки: если дифф меняет вход, токены, пароли, проверку ролей и прав, CORS или cookies, либо .env.example, — opus; в остальных случаях — sonnet. Модель ревьюера указывай явно.
- Завершение ветки: всегда вариант «Push and create a Pull Request». Локальный merge в main запрещён — PR вливаю я сам после ревью и зелёного CI.

### Тесты
- Строгий TDD (superpowers:test-driven-development): сначала падающий тест, потом код.
- Тесты и спеки, которые уже есть в main, НЕ изменяй и НЕ удаляй без моего явного разрешения. Если такой файл мешает — остановись, объясни причину и предложи варианты. Тесты, созданные в текущей ветке, править можно.
- «Готово» = команда «Все проверки разом» из раздела «Команды» проходит полностью (плюс то, что добавлено к «готово» в разделах про стек).

### Правка файлов
- Файлы проекта меняй только инструментами Edit и Write. Не переписывай файлы shell-командами и скриптами (sed -i, perl -i, скрипты на Python или Node, >, >>, tee, heredoc): хуки проекта (защита тестов, форматирование) срабатывают только на Edit и Write, а sed при неоднозначном совпадении молча меняет все вхождения.
- Можно: команды, которые меняют файлы по своему назначению (npm install, генераторы, миграции, форматтеры, git), и временные файлы вне проекта.
- Если одну и ту же замену нужно сделать во многих файлах, не обходи правило, а сначала спроси меня.
- Чекбоксы в плане отмечай через Edit. Строки шагов в разных задачах одинаковые («Step 1: …»), поэтому добавляй в old_string соседние строки, пока фрагмент не станет уникальным; replace_all не используй.

### Git
- Ветки, коммиты и PR — на английском. Коммиты в стиле Conventional Commits: feat:, fix:, test:, refactor:, docs:, chore:.
- commit, push, merge и создание PR выполняются только после моего подтверждения — это обеспечивают права в .claude/settings.json. Не пытайся их обойти.
- В коммитах и PR не добавляй строку Co-Authored-By и подпись «Generated with Claude Code».

### Язык и общение
- Общайся со мной по-русски, простыми словами: я учусь и не всегда читаю код целиком.
- Термины поясняй при первом упоминании в сессии.
- После изменений кратко говори, что сделано и зачем.
- Документация (спеки, планы, README, docs/product/) — на русском. Код, имена, комментарии в коде, ветки, коммиты, PR — на английском.
- Уточняющие вопросы — по правилам из раздела «Требования и цикл фичи» → «Вопросы».

### Секреты
- Секреты — только в .env (не попадают в git). В репозитории лежит .env.example с фиктивными значениями.
- Файлы .env ты прочитать не можешь (запрет в настройках). Имена всех переменных окружения смотри в .env.example. Если нужны новые переменные — добавь их в .env.example и попроси меня перенести их в .env.
