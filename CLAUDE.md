# TimeAudit — правила проекта

## О проекте
<!-- prd:about:begin -->
TimeAudit — веб-приложение (SaaS) для личного аудита времени: таймер на задачах, норма и баланс по рабочему графику, задачи по направлениям и проектам, обучение (курсы и книги с прогрессом) и отчёты. Каждый пользователь ведёт учёт только для себя; интерфейс на русском (основной) и английском, на компьютере и телефоне. Описание продукта — docs/product/project.md, термины и имена в коде — docs/product/glossary.md, общие правила — docs/product/rules.md.

## Структура
- backend/  — Python 3.13, FastAPI, SQLAlchemy 2 (синхронно), Alembic, Pydantic 2, PostgreSQL. Пакеты — только через uv.
- frontend/ — Next.js (App Router), TypeScript, Tailwind CSS, shadcn/ui. Пакеты — npm.
- docker-compose.yml — PostgreSQL для разработки.
- docs/ — документация: требования (docs/product/), спеки и планы Superpowers (docs/superpowers/), отложенное (docs/DEFERRED.md).
- .claude/ — настройки Claude Code и скиллы проекта (prd-*).
Правила написания кода — в backend/CLAUDE.md и frontend/CLAUDE.md.

## Команды
БД (PostgreSQL в Docker), из корня:  docker compose up -d --wait
Бэкенд, из папки backend/:
- запуск:          uv run uvicorn app.main:app --reload --port 8010
- тесты:           uv run pytest
- линтеры и типы:  uv run ruff check . && uv run ruff format --check . && uv run mypy app
- миграции:        uv run alembic upgrade head
- новая миграция:  uv run alembic revision --autogenerate -m "add example table"
Фронтенд, из папки frontend/:
- запуск:          npm run dev   (http://localhost:3010)
- проверки:        npm run lint && npm run format:check && npm run typecheck
- unit-тесты:      npm run test       (Vitest)
- e2e-тесты:       npm run test:e2e   (Playwright; нужна запущенная БД — бэкенд и фронт Playwright поднимает сам; не запускать одновременно с pytest — обе используют time_audit_test)
- типы API:        npm run gen:api    (берёт схему из кода бэкенда — запускать бэкенд не нужно)
Все проверки разом, из корня: ./scripts/check.sh

## Тесты (стек)
- Бэкенд — pytest с настоящим PostgreSQL (БД time_audit_test). Внешние сервисы мокаем.
- Фронтенд: Playwright — пользовательские сценарии и UI; Vitest — только чистая логика без React и DOM.
- Если менялся UI, к «готово» добавляются e2e-тесты.

## Тексты интерфейса
- Тексты интерфейса не пиши строками в коде — только через файлы переводов (ru и en). Основной язык — русский.

## Библиотеки
- Перед использованием API библиотек сверяйся с документацией: для Next.js — встроенная документация frontend/node_modules/next/dist/docs/ (см. frontend/AGENTS.md), для остальных библиотек — Context7.
- Новые зависимости: бэкенд — uv add, фронтенд — npm install. Каждую новую зависимость упоминай в плане и объясняй, зачем она нужна.

## Процесс разработки

### Задачи и ветки
- Новая задача — это новая фича, исправление или служебная правка, которую я явно начинаю (в том числе запуск /prd-project, /prd-features, /prd-feature). Продолжение начатой задачи (планирование, обсуждение, выполнение плана, правки после ревью, /prd-spec и /prd-done в ветке этапа) — это НЕ новая задача, даже если это новая сессия.
- Когда я начинаю новую задачу, до brainstorming и любых изменений файлов предложи ветку: имя (feature/<кратко>, fix/<кратко>, chore/<кратко> или docs/<кратко>) и от какой ветки её создать (обычно main после git pull). docs/ — для /prd-project, /prd-features и описания уже сделанных фич. Если есть открытые PR (`gh pr list`) или незакоммиченные изменения — упомяни их. Создавай ветку только после моего ответа.
- На main файлы не меняй и не коммить. Если ты на main, а нужно изменить файлы, — спроси меня.
- Git worktrees не используем: работаем в этой папке на обычной ветке (ответ на вопрос using-git-worktrees — «нет», спрашивать не нужно).

### Superpowers
- Спеки и планы сохраняй в пути по умолчанию Superpowers (docs/superpowers/specs/ и docs/superpowers/plans/) и пиши их на русском.
- План выполняй через superpowers:executing-plans. Выбор способа выполнения в конце writing-plans не предлагай. Subagent-driven — только по моей просьбе.
- Визуальный помощник brainstorming (браузер) не предлагай.
- Финальное ревью ветки: если дифф меняет вход, токены, пароли, проверку ролей и прав, CORS или cookies, либо .env.example, — opus; в остальных случаях — sonnet. Модель ревьюера указывай явно.
- Завершение ветки: всегда вариант «Push and create a Pull Request». Локальный merge в main запрещён — PR вливаю я сам после ревью и зелёного CI.

### Тесты
- Строгий TDD (superpowers:test-driven-development): сначала падающий тест, потом код.
- Тесты и спеки, которые уже есть в main, НЕ изменяй и НЕ удаляй без моего явного разрешения. Если такой файл мешает — остановись, объясни причину и предложи варианты. Тесты, созданные в текущей ветке, править можно.
- «Готово» = команда «Все проверки разом» из раздела «Команды» проходит полностью (плюс то, что добавлено к «готово» в разделах про стек).

### Правка файлов
- Файлы проекта меняй только инструментами Edit и Write. Не переписывай файлы shell-командами и скриптами (sed -i, perl -i, скрипты на Python или Node, >, >>, tee, heredoc): хуки проекта (защита тестов, форматирование) срабатывают только на Edit и Write, а sed при неоднозначном совпадении молча меняет все вхождения.
- Можно: команды, которые меняют файлы по своему назначению (npm install, генераторы, миграции, форматтеры, git), и временные файлы вне проекта.
- Если одну и ту же замену нужно сделать во многих файлах, не обходи правило, а сначала спроси меня.
- Чекбоксы в плане отмечай через Edit. Строки шагов в разных задачах одинаковые («Step 1: …»), поэтому добавляй в old_string соседние строки, пока фрагмент не станет уникальным; replace_all не используй.

### Git
- Ветки, коммиты и PR — на английском. Коммиты в стиле Conventional Commits: feat:, fix:, test:, refactor:, docs:, chore:.
- commit, push, merge и создание PR выполняются только после моего подтверждения — это обеспечивают права в .claude/settings.json. Не пытайся их обойти.
- В коммитах и PR не добавляй строку Co-Authored-By и подпись «Generated with Claude Code».

### Язык и общение
- Общайся со мной по-русски, простыми словами: я учусь и не всегда читаю код целиком.
- Термины поясняй при первом упоминании в сессии.
- После изменений кратко говори, что сделано и зачем.
- Документация (спеки, планы, README, docs/product/) — на русском. Код, имена, комментарии в коде, ветки, коммиты, PR — на английском.
- Уточняющие вопросы — по правилам из раздела «Требования и цикл фичи» → «Вопросы».

### Секреты
- Секреты — только в .env (не попадают в git). В репозитории лежит .env.example с фиктивными значениями.
- Файлы .env ты прочитать не можешь (запрет в настройках). Имена всех переменных окружения смотри в .env.example. Если нужны новые переменные — добавь их в .env.example и попроси меня перенести их в .env.

## Требования и цикл фичи

### Где что лежит
- docs/product/ — требования к продукту, источник правды о том, как программа должна работать:
  - project.md — цель, роли, ограничения, что не входит в проект;
  - glossary.md — термины и их имена в коде;
  - rules.md — общие бизнес-правила (BR-01, BR-02, …);
  - features.md — список фич: MVP, порядок, зависимости, статусы;
  - features/F-xx-<имя>.md — описание фичи: сценарии, правила, критерии приёмки (AC-1, …), этапы (F-03.1, …), история.
- docs/DEFERRED.md — отложенные задачи и замечания ревью (технический долг, не фичи).
- Скиллы: /prd-project, /prd-features, /prd-feature, /prd-spec, /prd-done. Запускаю их только я.
- Файлы в docs/product/ меняй только в рамках prd-скиллов и правил этого раздела.

### Вопросы (для любых задач)
- Уточняющие вопросы — одним нумерованным списком: к каждому предлагай варианты, отмечай рекомендуемый и объясняй почему. Если ответ на один вопрос меняет остальные — сначала задай только его.
- Количество вопросов не ограничено. Если после моих ответов появились новые вопросы — задай их так же. К работе переходи, только когда вопросов не осталось.
- Бизнес-логику (сценарии, правила, роли, права, приоритеты, что входит и что не входит) сам не решай: спроси или вынеси своё допущение мне на подтверждение. Сам решай только технические мелочи с очевидным стандартным ответом — и перечисляй их (в спеке — разделом «Решения, принятые Claude»).
- Не спрашивай то, на что уже отвечают docs/product/, спеки или код.

### Ветки
- Запуск /prd-project, /prd-features, /prd-feature и исправление бага — это новая задача.
- /prd-project, /prd-features и описание уже сделанной фичи (/prd-feature в режиме «описать уже сделанное») — ветка docs/<кратко>. /prd-features сразу после /prd-project — в той же ветке.
- Этап фичи — ветка feature/<кратко>. Описание фичи (/prd-feature), спека (/prd-spec), план, код и /prd-done идут в этой ветке и попадают в main одним PR. Спека, план, выполнение и /prd-done в ветке этапа — продолжение задачи, а не новая.

### Цикл этапа фичи (Superpowers)
- Brainstorming по этапу запускается через /prd-spec. Перед вопросами прочитай описание фичи и docs/product/project.md, glossary.md, rules.md.
- В имени файла и в заголовке спеки и плана указывай ID этапа (например, f-03-1).
- Термины — только из glossary.md, имена в коде — из его колонки «В коде». Нужен новый термин — спроси меня.
- Спека одобрена и закоммичена — стоп: writing-plans не запускай, назови путь к спеке. План я запущу сам в новой сессии.
- План записан и закоммичен — стоп: выполнение не начинай и способ выполнения не предлагай. Выполнение я запущу сам в новой сессии.
- Нашёл при планировании пробел или противоречие в спеке — задай вопросы, ответы внеси в спеку, потом продолжай план.
- Спека или план расходятся с описанием фичи — остановись и спроси, что правим: описание или спеку.
- Перед завершением ветки этапа (до finishing-a-development-branch) напомни мне запустить /prd-done <этап> и дождись.

### Баги
До правок найди описание фичи (через docs/product/features.md) и скажи мне, какой это случай:
1. Описание говорит одно, а программа делает другое, или что-то явно сломано (ошибка, падение, кривой экран) — чини, описание не меняй. Если ошибка в служебной части, к которой нет описания фичи, — тоже этот случай.
2. Программа делает то, что описано, а я хочу иначе — это не баг: остановись и предложи /prd-feature F-xx.
3. Описание об этом молчит — спроси меня, как должно быть; допиши правило в описание фичи (общее для нескольких фич — в rules.md) в этой же ветке, потом чини.

### Отложенное
- Остались после ревью отложенные замечания — запиши их в план (раздел «Отложенные замечания ревью») и добавь ссылку на этот раздел в docs/DEFERRED.md в той же ветке.
- Пункт из docs/DEFERRED.md берём в работу в ветке chore/<кратко>; когда сделано — удали пункт.
